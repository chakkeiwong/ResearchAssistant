## North-Star Mission

Let another user or agent start from an idea, topic, title, DOI, or paper and
run an auditable exploratory literature-survey evidence workflow through one
discoverable command:

```bash
ra survey run-public-source-workflow \
  --topic "<topic>" \
  --out <mission-dir>

ra survey run-public-source-workflow \
  --topic "<topic>" \
  --seed "<paper-id-or-title>" \
  --out <mission-dir>
```

The first form is the idea/topic input mode implemented and locally validated
in M17. The second preserves the explicit title/identifier input mode. M18 now
establishes identified local Git/install reproducibility in the observed
environment. Live bootstrap quality remains outside M17/M18.

The workflow asks once for bounded public discovery, persists that decision,
executes every permitted local and public discovery step, exposes source,
scientific-uncertainty, and external-action boundaries rather than hiding them,
and produces either:

- a lineage-valid, source-grounded qualitative assessed terminal within its
  recorded scope; or
- an honest terminal or boundary stop with the exact smallest next action.

The mission does not promise literature completeness, universal scientific
correctness, autonomous human judgment, exhaustive providers, unattended
production operation, or permission for credentials, private, paid, or
unbounded sources.

## Skeptical Plan Audit

The plan was audited before any execution for wrong baselines, proxy promotion,
missing stop conditions, unfair comparisons, hidden assumptions, stale context,
environment mismatch, and artifact fitness.

Findings and corrections:

1. The mission/CLI baseline is internally inconsistent: the mission accepts an
   idea or topic, while the CLI and mission-state contract require at least one
   seed. M17 must close this locally before claiming the north-star interface.
2. The correct reproducibility baseline is the M16 dirty-tree close, not a
   commit. Therefore M18 precedes every promotion-oriented live run.
3. The Phase 10 proposed Git manifest is not path-complete for M16; it names
   Phase 10 surfaces but cannot by itself prove all Phase 1-9 product/runtime
   dependencies are committed. M18 must regenerate a transitive include set.
4. A Phase 11 metadata smoke is a boundary/integration diagnostic only. It
   cannot close citation recall, source retrieval, scientific assessment, or product
   usability gaps.
5. Existing `source-fetch`, PDF, and download commands are not automatically
   approved production transports for the one-command mission. M21 must adapt
   or wrap them under the exact mission capability, lineage, caps, rights, and
   write-root contract.
6. A string such as `human_reviewed_passed` is not scientific evidence. The
   active M22 interface requires source-grounded qualitative interpretation,
   exact nonclaims, and an evidence audit; legacy receipt mechanics are not
   continuation authority.
7. One successful topic cannot establish reliability or completeness. M22 uses
   a small predeclared mission matrix and interprets provider/result counts as
   descriptive only.
8. `ready_for_prose` is a within-recorded-scope workflow terminal, not a
   scientific or product-readiness certificate.
9. Git integration, network access, source/PDF retrieval, scientific claim
   promotion, and external human decisions are separate authority boundaries.
   No milestone may infer one authorization from another.

With these corrections, the program's artifacts answer their stated questions
without treating proxies as promotion evidence.

Before any M17-M23 execution, create or refresh a dedicated subplan for that

review. No master-program paragraph substitutes for a dedicated subplan.

Every dedicated subplan must state:

- required artifacts and edit/write allowlist;
- required checks, tests, and reviews;
- evidence contract, including baseline, primary criterion, hard vetoes,
  explanatory-only diagnostics, and nonclaims;
- research intent ledger when live, stochastic, source, review, or
  decision-making work is involved;
- forbidden claims and actions;
- exact next-milestone handoff conditions, or M23 terminal completion/blocker
  handoff conditions; and
- stop conditions, distinguishing candidate failure from harness/boundary
  invalidity.

At the end of every milestone, the supervisor must:

1. run the required local checks and affected regression/boundary gates;
2. write a milestone result/close record with commands, manifests, evidence,
   decisions, nonclaims, and unresolved boundaries;
3. for M17-M22, draft or refresh the next milestone's dedicated subplan; and
4. for M17-M22, review that next subplan for consistency, correctness,
   feasibility, artifact coverage, inherited conditions, and boundary safety
   before any next execution.

M23 is the terminal exception: it has no successor subplan. After the M23
result/audit repair loop converges, the supervisor writes one ordinary close
record, refreshes the master program and reset memo, and records the exact Git,
wheel, command-ledger, replay, capability, and limitation evidence. It then
terminates with accomplished-within-scope or an exact blocker. It must not
invent or review an automatic post-M23 milestone.

Every milestone then uses this visible loop:

```text
PRECHECK
  verify prior handoff, exact hashes, permissions, and absent output roots
  run skeptical plan audit
  restate evidence contract and research intent

EXECUTE_MINIMAL
  perform the smallest safe implementation or diagnostic slice

ASSESS
  run catching checks first, then affected boundary and regression gates
  write the milestone result and classify hard vetoes versus explanatory data

REVIEW
  use a fresh read-only reviewer on the frozen material surface
  if fixable: patch visibly, rerun focused checks, and rereview
  stop after five rounds on the same material blocker unless the user explicitly authorizes more

HANDOFF
  write current result
  if M17-M22: refresh and review the next dedicated milestone subplan
  if M23: write the result, reconcile controls, run terminal replay/audit, and close or block
```
